# Свой код, LangChain, LlamaIndex: сравнение на одном пайплайне

Все три движка `/ask?engine=` используют один и тот же поиск (`app/rag/retrieval.py`, режим
rerank) и одну и ту же модель. Отличается только обвязка: как собирается промпт, как вызывается
LLM, как возвращаются источники. Так сравнение честное: разница в коде, а не в данных.

| | plain (`generation.py`) | LangChain (`frameworks/langchain_chain.py`) | LlamaIndex (`frameworks/llamaindex_engine.py`) |
|---|---|---|---|
| Строк кода обвязки | ~80 | ~60 | ~55 |
| Как собирается пайплайн | явные вызовы: search → messages.create | LCEL: `{"context": retriever \| format, "question": passthrough} \| prompt \| llm \| parser` | `RetrieverQueryEngine(retriever, response_synthesizer)` |
| Цитаты | **посимвольные**, от Claude API (`citations.enabled`): цитата, документ, кусок | только список кусков, ушедших в контекст | только `source_nodes` |
| Контроль промпта | полный: куски уходят `document`-блоками, system — наш | полный, но куски склеиваются в одну строку | шаблон наш, но LlamaIndex сам решает, как резать контекст по окну (`response_mode`) |
| Обработка ошибок API | по классам SDK: 429/5xx → 503, 4xx → 502 | исключения SDK пролетают сквозь цепочку, ловить снаружи | то же |
| Смена провайдера | переписать `ClaudeGenerator` | одна строка: другой `BaseChatModel` | одна строка: другой `LLM` |
| Подмена для тестов | фейковый клиент SDK | `FakeListChatModel` из коробки | `MockLLM` из коробки |
| Что прячет | ничего | второй вызов поиска (retriever.invoke + цепочка) — видно только если считать запросы | как именно куски уместились в промпт (`compact` склеивает) |
| Вес зависимостей | `anthropic` | `langchain-core` + `langchain-anthropic` (~30 пакетов) | `llama-index-core` + llms (~60 пакетов) |

## Что видно на практике

- **Цитаты — главное отличие.** В plain Claude цитирует дословно, и цитата сопоставляется с
  куском по `document_index`. Во фреймворках «источник» — весь кусок, который был в контексте;
  действительно ли модель на него опиралась, неизвестно. Для продукта с «покажи, откуда» это
  решающий аргумент.
- **LCEL читается как схема** и делает подмену компонентов тривиальной. Но первые 30 минут
  уходят на то, чтобы понять, что `retriever | RunnableLambda(...)` — это уже runnable, а словарь
  в начале цепочки превращается в `RunnableParallel`.
- **LlamaIndex заточен под RAG**: retriever + synthesizer — ровно та пара, что нам нужна.
  Обратная сторона — свои шаблоны и свой `Settings`, их приходится переопределять.
- **Второй поиск в LangChain-варианте** — это я оставил намеренно: чтобы отдать источники,
  нужны документы из retriever'а, а цепочка их внутрь не возвращает. Правильное лечение —
  `RunnableParallel`, который прокидывает `docs` дальше, или `retriever.with_config`. Хорошая
  задача на понимание LCEL.
- Метрики поиска у всех трёх одинаковые по построению (один `search()`), поэтому evals из
  этапа 7 сравнивать между движками бессмысленно; сравнивать имеет смысл качество ответов —
  LLM-as-judge, когда появится доступ к модели.

## Рекомендация

Прототип или много провайдеров — фреймворк (LangChain, если пайплайн сложнее RAG; LlamaIndex,
если это именно индексация и поиск по данным). Продакшн с одним провайдером, где важны цитаты,
контроль промпта и обработка ошибок, — тонкий свой код поверх официального SDK. Понимать, что
фреймворк делает внутри, нужно в обоих случаях, иначе отлаживать нечего.
